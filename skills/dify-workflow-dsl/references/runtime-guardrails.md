# Dify 工作流运行时鲁棒性门禁

## 模板语法域与迁移

| 活动字段 | 声明 | 引用 |
|---|---|---|
| 普通插值字段、LLM basic.text | 图变量 | `{{#node_id.output#}}` |
| template-transform.data.template | data.variables 的 variable/value_selector | `{{ alias }}` |
| LLM jinja2_text | prompt_config.jinja2_variables | `{{ alias }}` |

先确定字段实际采用的编辑模式，再检查活动文本。`basic` 缺省读取 `text`，Jinja 模式读取 `jinja2_text`；不以非活动字段的旧内容判定运行失败。Jinja 别名需声明，局部循环变量、宏参数、内置变量按 Jinja AST 作用域处理；不能用简单正则推断全部未声明变量。

迁移逐项记录源占位符、目标选择器/别名、数据类型和容器作用域，转换后再次扫描最终文件。源平台插值如 `${...}`、basic 中预期执行的 `{% ... %}`、Jinja 中活动的 `{{#...#}}` 均需修复。字面示例、注释、raw 区域和普通业务文本保持原意，不做全文件无差别替换。目标版本不支持的过滤器/扩展必须另行核实；本地标准 Jinja2 解析不等于 Dify 沙箱支持全部模板能力。

## Code 节点编译与回放

- 生成、迁移或修改 Code 后，对最终节点源码按 `code_language` 做语法检查：Python 用 `compile`，JavaScript 用可用解析器或 Node 语法检查；缺少相应工具时记录未检查，不能全部按 Python 编译。
- 每个节点独立导入自身使用的模块/别名，检查 `main` 参数与变量绑定、返回键与 `outputs` 类型。编译无法发现缺少导入；调用回放时覆盖新增分支和模块调用路径。
- 回放前检查源码有无网络、文件写入、子进程或外部调用。纯计算函数可在隔离临时目录和有超时限制的子进程中回放；这只是环境隔离，不是安全沙箱。未知或有副作用的代码不直接在宿主机 `exec`，使用禁用副作用的 mock/真正受限环境；不可安全回放时标记 `unknown`。
- 最小样本覆盖新增/修改逻辑的正常、空值/缺字段及关键错误路径。断言输出键、类型和关键业务结果；不追求固定测试数量。原有未修改 Code 做语法检查，只有受影响路径才追加回放。
- `NameError`、`ImportError`、返回类型不符和预期路径失败均为交付阻断项。测试异常处理时应断言预期错误，不把预期失败误报为回归失败。
- 本地回放独立记录；未在目标 Dify Sandbox 运行，不据此标记 `runtime_ready: true`。

## JSON 内部传输与外部接口

把中间节点的传输表示与调用方接口分开定义。已有对象链路正常时保留原表示；只有已核实的对象层级限制、节点或子工作流字符串契约等具体需要时，才在必要边界序列化，不把所有中间值统一改为字符串。

### 边界规则

1. 先记录外部字段名、类型和业务结构，再标明内部哪些边传 `object`、哪些边传 JSON `string`。内部改造不自动授权修改外部契约。
2. 发送端使用 JSON 序列化器，输出声明与实际值一致；例如 Python 使用 `json.dumps(value, ensure_ascii=False, allow_nan=False)`，对应输出声明 `string`。禁止手工拼接 JSON、用 `str(dict)` 代替序列化或重复编码已经约定为 JSON 文本的值。
3. 消费端需要读取业务字段时先解析为局部对象，不直接用对象字段选择器访问字符串。内部仅作透传时不反复解析/序列化。只解码契约规定的层数，不循环解码到“看起来像对象”。
4. 对外约定为对象时，在最终汇合后或出口适配节点严格解析，检查顶层类型及约定的必要字段，再返回真实对象；Python 返回 `dict`，Code 对应输出声明为 `object`，End 选择该输出且 `value_type: object`。最终不再 `json.dumps`，调用方无需对该字段二次 JSON 解析。
5. 严格解析应拒绝空文本、畸形 JSON、重复键及非有限数值；按契约处理缺字段和顶层类型。数组/标量只在约定允许时包装为语义对象。不得把失败替换为 `{}`、丢弃字段或偷偷改回字符串。模型输出修复应在独立、有限的修复路径完成，出口适配器只负责校验与类型转换。
6. 既有外部接口要求 `string` 时继续保留；输出类型变更获得授权后才调整出口及调用方。内部字符串传输可以缓解中间节点对象层级限制，但不能绕过出口的对象层级、大小或其他运行约束。最终对象仍超限时，按已授权契约拆分出参或调整结构；无法兼容时报告冲突，不静默删减或改类型，也不把某实例的具体层数写成全局常量。

### 变更验收

- 对正常、空集合、中文/转义字符及代表性深层数据做序列化往返，比较业务字段、数组顺序和值是否保持一致。
- 对空文本、畸形 JSON、错误顶层类型、重复键和非有限数值验证显式失败；有双重编码样本时确认不会被无约定地递归解包。
- 检查每个受影响边的实际值与声明类型，尤其是互斥分支汇合、子工作流输入、最终 Code 返回值和 End 选择器；只修改 End 的类型标记不足以完成转换。
- 本地解析与往返通过只证明转换逻辑。目标运行验收需直接检查 `data.outputs.<字段>` 的实际类型与完整结构，并确认最终对象未触发目标实例限制。

## 模型参数

`completion_params` 是 provider 动态字段。先读取目标 schema 或同租户成功配置，核对类型、范围、步长、精度和枚举。缺少 schema 的新建任务中，`temperature`、`top_p` 可使用最多两位小数的保守值；已有高精度参数保留并标待核实，禁止自动舍入改变模型行为。

扫描器的 `MODEL_PARAM_PRECISION` 是 warning，不是平台拒绝证据；`NaN/Infinity` 等非有限数值是 error。允许高精度的开关不豁免非有限数值检查。动态参数仍需 provider 验证，不能从 YAML/Pydantic 解析成功推导合法性。

## 本地扫描

命令、退出码和覆盖范围统一见 [验证步骤](validation.md)。完整模板语法检查需要 PyYAML 和 Jinja2；缺依赖时明确报告。脚本只覆盖部分静态门禁，不自动检查 Code 导入、选择器、真实分支覆盖或 fallback 追踪。

## 真实运行验收（已授权时）

为本次变更建立路径表：输入条件、预期分支、实际节点 ID、终态、fallback/重试和输出契约。只执行本次已授权的运行及副作用；本地回放不自动升级为线上测试。

1. 使用能到达目标节点的最小输入，覆盖修改涉及的分支、容器和错误路径。
2. 检查终态及最终输出的类型/关键值；流程显示 SUCCESS 仍需查追踪。
3. 搜索节点异常、默认值输出、重试耗尽及目标错误签名。fallback 若掩盖失败，相关节点不能记为运行通过；预期的降级行为单独验收并明确说明。
4. 未执行分支保持 unknown；单次成功不能证明整张图全部运行正确。
5. Cloud 测试后重新 GET 草稿，核对保护字段并记录最新 hash。模型检查、画布渲染、草稿同步、发布和真实执行分别报告。
