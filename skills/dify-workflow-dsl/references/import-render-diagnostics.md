# Dify 导入与渲染诊断

## 适用症状

- 导入后页面显示“渲染此组件时发生了意外错误”。
- 控制台出现 React #130，错误参数包含 `undefined`。
- 同一 App 的旧标签页报错，而新标签页可以显示画布。

## 先核对图结构

从目标实例最新 `/workflows/draft` 回读服务器草稿，不以导入文件名、页面标题或旧标签页内存状态代替回读。至少核对：

- 节点数、连线数和 `data.type` 分布。
- 每个节点的外层 `type` 与 `data.type`。
- Iteration 的 `start_node_id` 是否指向存在的起始节点。
- 起始节点是否具有正确的 `parentId`、容器元数据和专用 wrapper。

强制组合：

| 运行类型 | 外层 wrapper |
|---|---|
| `iteration-start` | `custom-iteration-start` |
| `loop-start` | `custom-loop-start` |

普通节点工厂若无条件返回 `type: custom`，会把 `iteration-start` 错配成普通节点。Dify 后端可能仍能导入或保存这份图，但前端依据外层 wrapper 选择 React Flow 组件时会得到未定义组件，从而触发 React #130。生成器应显式映射这两个例外，并用测试锁定 wrapper 和 `data.type` 两层。

## 再区分真实错误与旧标签页残留

修正并重新导入后，旧标签页可能继续保留导入前已经崩溃的 React 树。诊断时：

1. 保留旧标签页作为对照，不在其中反复点击“重试”得出结论。
2. 用同一登录会话新建标签页打开相同 App URL。
3. 等待草稿请求完成，检查画布 DOM 和新标签页产生的控制台错误。
4. 同时回读服务器最新草稿，确认专用 wrapper 已实际保存。

服务器草稿仍错误时继续检查 DSL；全新标签页仍复现只是排除了旧标签页残留，仍需检查前端版本、插件和接口响应，不能单凭复现断言 DSL 有错。若服务器草稿正确、全新标签页正常而旧标签页报错，应报告为旧页面残留，并建议关闭旧标签页或强制刷新；不要再次修改或覆盖草稿。

## 分开报告检查清单

画布正常渲染不等于可发布。模型、工具、知识库和凭证缺失会出现在检查清单中，应作为 `publish_ready` 阻断项单独报告，不得称为组件渲染错误。例如 `dataset_ids: []` 可以成功导入并显示节点，但知识库为空时仍不能发布或运行对应检索链路。

## 结论边界

- YAML 可解析：仅证明解析通过；`schema_valid` 还需目标版本字段检查。
- wrapper、容器和变量结构正确：可支持 `graph_valid`，但不自动证明目标租户可导入。
- 目标实例回读正确且全新标签页正常：才可确认本次草稿已同步并可渲染。
- 检查清单清零、发布和真实运行必须分别验证。
